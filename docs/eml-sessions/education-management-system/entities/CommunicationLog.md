# CommunicationLog  ·  standalone  ·  category: Student Support

**Role.** An auditable record of an operational message to a guardian about a student, including delivery failure. It records the subject and outcome rather than storing unnecessary message content.

**Placement.** Standalone. Failed messages across all families (`registrar-failed-communications`) are a list in their own right. Both `student_id` and `guardian_id` are optional, because a notice can concern a student without addressing one guardian, or the reverse.

## Fields

| Column | Type | Modifiers | Purpose |
|---|---|---|---|
| `id` | string | PK | The record's own identifier. Generated by the application and never keyed; it is never shown as a display value. |
| `student_id` | string | FK OPTIONAL | The student the message concerns. Optional only for a general guardian communication not tied to one child. |
| `guardian_id` | string | FK OPTIONAL | The guardian contacted. Optional only for an internal or student-only communication, but at least one recipient context is required. |
| `sent_by_id` | string | FK | The staff member accountable for the message or automated campaign that created it. |
| `channel` | string | — | How the message was attempted, which determines what delivery evidence and fallback action are possible. |
| `purpose` | string | — | Why the school contacted the family, used to keep sensitive safeguarding traffic out of broad academic and finance queues. |
| `status` | string | — | queued — waiting to send; sent — accepted by the channel; delivered — delivery confirmed; failed — no delivery and a reason requiring follow-up. |
| `subject` | string | — | A short non-sensitive description staff can recognise in a timeline. Do not place safeguarding details in this field. |
| `summary` | text | — | The minimum operational summary needed to understand the contact and promised follow-up, not a duplicate of the full message body. |
| `sent_at` | datetime | OPTIONAL | When the message left the school or the call occurred. Blank while it remains queued. |
| `delivered_at` | datetime | OPTIONAL | When the channel confirmed delivery. Blank for channels that do not provide confirmation. |
| `failure_reason` | text | OPTIONAL | Why delivery failed and what staff should correct before retrying, such as an invalid number or rejected email. |

## Enums

- `channel` → **CommunicationChannel**: email, sms, phone, post, portal, in_person
- `purpose` → **CommunicationPurpose**: attendance, academic, finance, safeguarding, admissions, general
- `status` → **CommunicationStatus**: queued, sent, delivered, failed

## Relationships

- `Student ||--o{ CommunicationLog` — concerns *(this side carries the foreign key)*
- `Guardian ||--o{ CommunicationLog` — receives *(this side carries the foreign key)*
- `Staff ||--o{ CommunicationLog` — sends *(this side carries the foreign key)*

**Indexes.** `CommunicationLog(guardian_id, status, sent_at)`

## Rules

### `communicationDeliveryControl` on `beforeUpdate` — **`%%action` decision table — it can act**

- `requireCommunicationFailureReason validation-error when: status == "failed" and failure_reason == null message: A failed communication needs a reason so staff can correct the address or choose another channel.`

## Hooks

None.

## Cross-entity effects

None. The entity is the record of a message, not the sender of one: nothing in the model writes a row. `notifyGuardiansOfStatusChange` on `Student` is the only notifier the model declares, and its handler is where a row would naturally be created, but the model does not say that it is.

## Open questions

By design it stores the subject and the outcome, not the message content. Whether a guardian-facing portal may show a guardian their own log depends on row-level scoping that `%%rbac` cannot express; the `guardian` role can read this entity as a role, not as a filter.
