Run the real stack

The whole application, in this tab

Page 09 compiles a model into a runtime that needs no install and no build step — which is what makes it start in ten seconds, and also what makes its interface a port of the real one rather than the real one. This page makes the other trade. It assembles the actual generated application, four hundred files of NestJS and TanStack Start, and hands them to a WebContainer: real Node.js compiled to WebAssembly, a real npm install, the real Vite build.

Everything before the install is the same code the command line runs. generateApplication and the WASM overlay are imported unmodified; what changes is the filesystem beneath them, which is a Map in this tab instead of a disk. That is the whole trick, and it is why what boots below is the application appwithai-wasm generate would have written rather than something assembled to look like it.

This needs the network, and a browser that allows cross-origin isolation. A WebContainer downloads its Node.js runtime from StackBlitz and then installs some two thousand packages from npm, so the first run is minutes rather than seconds and none of it works offline. Page 09 has neither requirement — if you want to see an application running quickly, start there.

    How this differs from page 09

    Both pages compile the same model with the same compiler. What they do afterwards is the whole difference, and it is a real trade rather than one being a lesser version of the other.

    Page 09 — the browser runtime

    • Starts in about ten seconds
    • No install, no build, works offline
    • PGlite in the tab, application server on a Worker
    • Its interface is a port of the generated one
    • Nothing to open and edit per entity

    This page — the real stack

    • Minutes, most of it npm install
    • Needs the network and cross-origin isolation
    • Real Node, real NestJS, real Vite build
    • The actual generated React front end
    • Four hundred files you can read and change

    What is honest about this

    The generation half is exercised on every commit: CI assembles the stack in a browser bundle and compares it, file by file, against what the command-line generator writes to disk. They match but for the nine font files, which are binary and are not carried in the JSON the templates arrive as — the application inside the WebContainer falls back to system typefaces because of it.

    The boot half is not exercised anywhere, and it is worth saying plainly why. WebContainers fetch their runtime from StackBlitz's own hosts, which are unreachable from the environment this was written in, so this page's install-and-start path has been written carefully and never once watched working. If it fails for you, the message below the button is the real one from the API rather than a guess, and everything up to that point — the model, the check, the four hundred files — has already happened in your tab and can be downloaded from page 09.
